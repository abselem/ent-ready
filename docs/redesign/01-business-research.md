# Продуктовая постановка редизайна ent-ready

Дата: 23.10.2026. Передача: бизнес-аналитик → UX/UI → системный аналитик/архитектор → ТЗ фронтенду. Статус: проектное направление; реализацию не начинали.

## Основания и границы исследования

Текущий localhost в браузере не исследовался по выбору пользователя: аудит текущего UI выполнен только по исходникам. Проверены текущие исходники frontend и предыдущий competitor-research.md, выполнены новый поиск и открытие официальных страниц. Ниже — наблюдения по публичной текстовой структуре, доступной веб-инструменту. Скриншоты, цвета, пространственные композиции и личные кабинеты конкурентов не проверялись; нельзя выдавать это за визуальный аудит отрисованных продуктов. Пользовательские интервью и аналитика ent-ready отсутствуют: удобство и метрики далее — гипотезы.

## Аудит текущих сценариев по коду

- **Ученик: выбрать предмет → тест → ответить → результат.** На /student уже есть назначенные тесты и поиск предметов. В student/page.tsx запросы по умолчанию дают [], но нет отдельного error/loading состояния: загрузка предметов способна выглядеть как «Предметы не найдены», сбой назначения — как отсутствие заданий. Приоритет P0: различать загрузку, пустое состояние, ошибку и результат поиска.
- **Ученик: подготовить полный ЕНТ.** /student/ent уже показывает структуру и требует профильные предметы. Нужна ясная пара «Тренировка по предмету / Полный ЕНТ», состав и объяснение перехода к профилю. Формат экзамена не пересматривать в рамках редизайна: он должен отражать серверную конфигурацию, без обещания соответствия официальному экзамену.
- **Прохождение и разбор.** student/tests/[id]/page.tsx сохраняет выбранное значение локально сразу, отправка answer выполняется отдельно. Требуется видимое различие «выбран / отправляется / сохранён / ошибка», без ложного подтверждения. can_see_answers и отложенный разбор уже существуют и сохраняются. Две цепочки декремента таймера в коде — риск корректности, архитектору отдельно проверить; дизайн таймера не исправляет логику. P0 для потери доверия/данных, P1 для визуальной последовательности.
- **Учитель: группы → тесты → публикация → результаты.** /teacher — список групп и создание; /teacher/tests — фильтр предмета и форма создания с группой, попытками, временем, публичностью и дедлайном. Сохранить операции; отделить список от редактирования визуально, давать публикации и доступу явные подписи. Ошибки запроса списка также нельзя выдавать за пустой список. P1.
- **Общий интерфейс.** Навигация ролей уже разделена; student/results имеет фильтры и сводку. globals.css задаёт светлую/тёмную тему и синий акцент, страницы используют разные max-width и смеси общих/локальных карточек, emoji и SVG. Это факт неоднородной реализации, не доказанная пользовательская боль. P1: единая шкала плотности, типографики, состояний и иконок.

## Два направления

**A. Спокойная учебная среда (рекомендуется).** Сохранить синий бренд и существующую навигацию ролей; нейтральный фон, компактные списки для работы учителя, умеренно цветные предметные карточки для ученика, один главный CTA в контексте. Экзамен — максимально ясный вопрос, время, прогресс, сохранение и завершение; декоративные блоки убрать из фокуса. Это предложение дизайна, не подтверждённый рыночный тренд.

**B. Энергичная подготовка.** Более выразительная типографика, цветные секции предметов, крупные акцентные карточки и видимая существующая активность/серия. Без новых наград, рейтингов, персонального плана. Возможный плюс — узнаваемость; риск — шум на мобильном экране и неодинаковый тон ученического/учительского сценария. Нужна сравнительная проверка прототипов.

Пользователь выбрал **A — спокойный учебный интерфейс**. Предметные акценты допускаются сдержанными, без игровой яркости. Альтернатива B оставлена только для сравнения, не для обязательного прототипирования. Основание рекомендации: ближе к действующим токенам и компонентам, охватывает обе роли, меньше риск расширить API или отвлечь от ответа. Это рабочая рекомендация для UX, а не одобрение новой функциональности.

## Первая итерация без расширения API

Включить оболочку обеих ролей и UI-токены; /student, /student/ent (выбор/подготовка), обычный тест /student/tests/[id] и его результат; /teacher и /teacher/tests. Для маршрутов вне итерации — проверить совместимость общих компонентов, без их полного перепроектирования.

Использовать существующие данные topics, groups/joined, groups/:id/tests, tests/:id, attempts/:id/answer и finish, ent/start, ent/attempts/my, groups, tests/mine и tests. Отдельные бейджи завершённости назначенного теста, дедлайна, продолжения попытки показывать только при подтверждённых данных/контракте. Не выводить статус из отсутствующего поля. Новые метрики прогресса, AI, платежи, рейтинги, локализацию всего продукта, гостевые тесты, новые уведомления и рекомендатель исключить. Локальный поиск/сортировка только по уже загруженным данным; не обещать глобальный поиск.

## Задание UX/UI и критерии передачи

1. Подготовить схемы потоков для ученика и учителя и короткие desktop/mobile макеты ключевых экранов A; альтернативный визуальный вариант B не обязателен, поскольку пользователь уже выбрал A. Референсы использовать как структурные принципы, без копирования фирменных активов.
2. Описать состояния: loading, empty, no-results, error/retry, denied/expired, pending/success/error записи, недоступный разбор, отсутствующие профильные предметы. Не изображать подтверждение сохранения до ответа сервера.
3. Определить UI-токены, компоненты, размеры касаний, фокус и клавиатурный порядок, светлую/тёмную палитру; проверить длинные названия и математические формулы. Цвет не должен быть единственным носителем правильности/ошибки.
4. Архитектор получает матрицу «экран → поля/действия текущего API → состояния → критерий», список границ итерации и открытых вопросов. Все пробелы контракта — явные блокеры конкретного элемента, без выдумывания эндпоинта.

## Проверка гипотез

На одних и тех же заданиях сравнить текущий интерфейс и прототип: найти назначенный тест; выбрать тренировку/ЕНТ; объяснить статус сохранения; завершить тест; учителю создать черновик и найти результаты. Метрики — успешность без подсказок, время, ошибки выбора и понимание статусов; фиксировать медиану и причины ошибок. Сначала снять baseline; численные цели роста пока не заданы. Минимальная приёмка до разработки: все переходы выполнимы, пользователи различают сохранённый и несохранённый ответ, отсутствуют вымышленные данные и новые API.

Для реализации: проверить клавиатуру, фокус, читаемость обеих тем и экранов 360/768/1440 px; длинные названия и формулы без потери содержимого; права и отложенный разбор не меняются. Автоматические события аналитики потребуют отдельного решения; для прототипа достаточно записи результатов исследования без персональных данных.
