# BRD v1.0: план внедрения и контракт A1

Дата: 2026-11-02. Статус: техническая постановка первого среза, не объявление готовности всего MVP.

## Источники и границы анализа

Прочитан полный BRD из пользовательского вложения `Вставленный текст.txt` (BRD v1.0). Проверены маршруты `handler/routes.go`, JWT middleware, обработчики групп и уроков, `handler/content_access.go`, миграции 001–024, состояние авторизации и API frontend. SMS.pdf — скан 20 страниц; визуальная сверка выполнена отдельно и зафиксирована в `docs/product/sms-brd-reconciliation.md`. Для первого среза принята явно указанная в сверке рабочая гипотеза приоритета уточнений BRD над ранним discovery PDF. Родители и attendance остаются P0 итогового MVP, но не включены в A1. Проценты видеопросмотра, тарифные числа и метрики макетов не становятся выдуманными данными интерфейса.

Текущий teacher создаёт группы сам, что отличается от матрицы BRD Owner/Admin; это сохраняется только в legacy personal режиме.

## Последовательность

1. **A1 — регистрация рабочих пространств.** Создание, список, настройки, состав и переключение. Изоляция только новых объектов organizations/members. Данные существующего кабинета не переносятся автоматически. Пользователь видит границу режима.
2. **A2 — tenant enforcement учебных данных.** План backfill с резервной копией, tenant_id на агрегатах, составные внешние ключи/проверки связей, scoped списки и прямые чтения/изменения/attempts/reviews. Запрет cross-tenant ссылок на группы, темы, вопросы и файлы. Устранение обходов через старые API; политика legacy-каталога. Только после независимых негативных тестов объявлять tenant isolation.
3. **A3 — приглашения и управление составом.** Истекающие одноразовые приглашения, отзыв, роли по организации, назначение преподавателя, memberships и история enrollment. Глобальная учётная запись не дублируется.
4. **A4 — дети/родители/согласия.** Предварительная запись, подтверждённая guardian связь, scoped student profile; запрещена самостоятельная привязка по одному ID ребёнка. Правовые тексты и условия активации задаются владельцем продукта.
5. **B — учебный процесс.** Курсы, публикация по времени, материалы/видео с подтверждаемыми событиями, прогресс, расписание/attendance. Не выдумывать просмотр видео и не приравнивать открытие к освоению.
6. **C — ДЗ/оценки.** Назначения, дедлайны/продления, idempotent submit, immutable attempts, optimistic lock проверки, draft/published grade, журнал и guardian read.
7. **D — пилот.** Уведомления, реальные метрики, подписки/квоты, аудит, backup/restore, нагрузка и тестирование изоляции.

## A1: сценарий и явные предположения

- Создавать организацию временно может только существующий глобальный teacher. Student/self_learning не получают self-service owner. Это ограничение первого среза, а не финальное правило BRD.
- Создатель становится owner только внутри новой организации; users.role_id и JWT role не меняются.
- Можно создать несколько организаций с одинаковым названием. Идентичность — ID, не название.
- В A1 добавление участников и приглашения ещё не включены. У созданной организации один owner; дополнительные роли в БД и тестовых fixtures нужны для проверки запретов и будущего расширения.
- Роли организации: owner/admin/teacher/student/parent. Platform admin — отдельная будущая модель, не глобальный доступ через owner.
- Настройки задаются организацией: timezone IANA, locale ru/kk, grading_scale points/5/10/100. Locale kk означает выбранную настройку, а не готовый перевод всего сайта. Grading_scale в A1 ещё не пересчитывает текущие legacy оценки.
- Новые организации не содержат существующие уроки/группы/тесты; создание организации не даёт доступа к чужим legacy ресурсам. Не передавать выбранный ID в старые API и не изображать tenant-фильтрацию, которой пока нет.
- Переключение — выбор рабочего пространства для просмотра его настроек/состава; сервер проверяет членство при каждом запросе. Локальный selected ID не является разрешением.

## A1 API, версия для параллельной реализации

Базовый путь `/api/v1`. Все запросы требуют существующую JWT-сессию. Организации не добавляются в access token; membership проверяется по БД на каждый org-запрос.

### Общие структуры

`OrganizationSummary` и detail имеют одинаковые non-null поля:

```json
{"id":1,"name":"Школа Progress","timezone":"Asia/Qyzylorda","locale":"ru","grading_scale":"points","role":"owner","created_at":"2026-11-02T10:00:00Z","updated_at":"2026-11-02T10:00:00Z"}
```

`role` — роль текущего пользователя именно в этой организации. Timestamp ISO8601/RFC3339. ID положительное целое.

`OrganizationMember` (краткий профиль, без email/phone/global role):

```json
{"user_id":2,"first_name":"Алия","last_name":"Тестовая","role":"teacher","joined_at":"2026-11-02T10:00:00Z"}
```

### Маршруты

| Метод/путь | Права | Тело/ответ |
|---|---|---|
| GET /organizations | Авторизован | 200 OrganizationSummary[], только active memberships; пустой список [] |
| POST /organizations | Только legacy teacher | name обязателен; timezone/locale/grading_scale optional; 201 OrganizationSummary с role owner |
| GET /organizations/:id | Active member | 200 OrganizationSummary; чужой/неактивный/not found →404 |
| PATCH /organizations/:id | Active owner/admin | Частичные name/timezone/locale/grading_scale, минимум одно поле; 200 OrganizationSummary |
| GET /organizations/:id/members | Active owner/admin | 200 OrganizationMember[], deterministic joined_at,user_id; пустой список [] |

POST defaults: timezone `Asia/Qyzylorda`, locale `ru`, grading_scale `points`. Name trim 1–120 символов, поддерживать кириллицу; whitespace-only запрещён. Timezone проверять time.LoadLocation; неизвестный IANA ID —400. Locale только ru/kk; grading_scale только points/5/10/100. Null для изменяемых non-null полей —400, пустая PATCH —400. Body не принимает user_id/role/tenant_id как средство назначения прав.

Ошибки в существующем формате `{ "error": "..." }`:

- 400: неверный ID, JSON, тип/граница/enum поля.
- 401: отсутствующая/неактивная JWT-сессия.
- 404 `organization not found`: организация отсутствует, membership отсутствует или inactive. Не раскрывать существование чужой организации.
- 403 `insufficient permissions`: active member известной ему организации с неподходящей ролью; POST запрещён не-teacher.
- 500 `internal error`: ошибки хранения, без SQL/секретов.

POST создаёт organization и owner membership одной транзакцией. При ошибке membership организация не остаётся. Пользователь не может самостоятельно задавать owner другого пользователя.

## A1 данные и владение файлами

Backend владеет:

- `db/migrations/025_organizations.sql`: organizations (id,name,timezone,locale,grading_scale,created_at,updated_at); organization_members (organization_id,user_id,role,status active/inactive,joined_at), UNIQUE(org,user), FK, enum CHECK и индексы. Не менять применённые миграции и данные 001–024.
- Фактический SQL source A1: `db/organization_queries/organizations.sql`; команда `sqlc generate -f sqlc.organizations.yaml`; output `db/organizationsqlc/`. Используется отдельная конфигурация, поскольку прежние SQL sources и generated legacy package имеют накопленный drift: общий запуск мог бы изменить несвязанный текущий API. Это техническая изоляция генерации, не новая модель хранения/ORM. `sqlc.yaml` и существующий `db/sqlc/` не меняются. Generated A1 также не редактируется вручную. Сведение legacy drift в основной pipeline — отдельная задача.
- `handler/organizations.go` и необходимые helpers; `handler/routes.go` org routes; meaningful integration tests в изолированной test БД.
- Транзакция через существующий pgx/sqlc pattern, без нового ORM/архитектуры.

Frontend владеет:

- Экран `frontend/src/app/teacher/organizations/page.tsx` в существующем layout, вход карточкой через `frontend/src/app/teacher/profile/page.tsx`. UX: `docs/design/organization-workspaces-a1.md`. Пять пунктов общей мобильной Nav сохраняются; дополнительная защита несохранённых настроек — `frontend/src/components/nav.tsx`.
- Фактические API-типы и функции выделены в `frontend/src/lib/organizations-api.ts`, который использует общий существующий клиент `api` из `frontend/src/lib/api.ts`. Основной interceptor/auth-flow не меняется.
- Состояние выбранной организации не должно менять global auth role и ключи текущих legacy запросов; при смене пользователя очищается.
- Ошибки, loading, пустой список, disabled submit, сохранение пользовательского ввода при ошибке. Сквозная доступность формы и мобильная ширина.

Координатор владеет интеграцией и решением конфликтов. Дизайнер не редактирует файлы разработчика. Tester пишет проверки отдельными назначенными файлами; не запускает против production.

## A1 критерии приёмки

1. Teacher создаёт организацию и сразу видит её в списке, настройки и себя как owner; повторный вход сохраняет организацию.
2. Создание двух организаций не меняет users.role_id и не даёт доступ к чужим groups/lessons/tests.
3. Teacher A не видит организацию B в списке; прямые GET/PATCH/members B возвращают404; подмена ID в localStorage не помогает.
4. Active teacher/student/parent membership видит detail, но PATCH/members возвращают403. Owner/admin может менять настройки/читать состав. Inactive membership получает404.
5. Student/self_learning не может создать организацию POST даже при обходе скрытой UI кнопки.
6. Невалидные поля/null/empty PATCH запрещены; сбой owner insert не оставляет пустую организацию.
7. В organization member response нет email, phone, global role_id, password_hash или session данных.
8. Старые personal teacher/student сценарии и доступы сохраняются; экран сообщает, что перенос учебных данных ещё не выполнен.
9. Пустой список сериализуется []; loading/error не выглядит как подтверждённое отсутствие организаций.
10. `sqlc generate`, gofmt, `go test ./...`, `go vet ./...`, frontend lint/build реально выполнены с фиксацией результата; БД тестовая.

## Deployment gate

`main.go` автоматически применяет все новые миграции при старте. Push при Railway auto-deploy означает production migration. Этот этап готовится локально, проверяется на отдельной БД и проходит review до отдельного решения о production-выкладке. Ранее разрешение на UI push не считать автоматическим согласованием нового переноса/изменения схемы БД.

## Решения, которые нельзя выдумывать

До соответствующего этапа нужны: возраст/активация ребёнка и основания согласий; право учителя зачислять; политика late/resubmit; формула оценок/весов и исправления опубликованной оценки; тарифные квоты/цены; пилотная нагрузка; retention/export/delete; правила миграции публичных legacy материалов. A1 не блокируется этими вопросами, потому что не активирует соответствующие процессы.

## Финальное архитектурное review A1 — 02.11.2026

Метод: независимое read-only чтение итоговых backend/frontend файлов, миграции, SQL source/generated A1 и UX. Runtime/API/БД тесты в этом review не запускались: независимый tester эксклюзивно использует изолированную БД. Результаты ниже являются выводами по коду, не подменяют его отчёт.

Блокирующих расхождений с принятым контрактом A1 по проверенному коду не обнаружено:

- Маршруты организаций находятся в secure JWT-группе, создание дополнительно ограничено текущей серверной legacy teacher ролью. Owner назначается сервером в транзакции с созданием организации, глобальная роль users не меняется.
- GET list/detail отбирает active membership; чужой/неактивный ID скрывается404. PATCH требует owner/admin и повторяет проверку actor membership в UPDATE SQL. Members проверяет менеджера и дополнительно actor membership в SQL. Нет ID организации, которому доверяют только на основании frontend/localStorage.
- Поля JSON разрешены явно, payload ограничен4096 байт, null/пустой объект/лишние поля/несколько JSON объектов отвергаются. Name проверяется в Unicode символах, timezone поддерживается встроенными tzdata, locale/grading enum соответствуют контракту. PATCH меняет только переданные поля.
- Summary/detail содержат согласованные поля; members возвращает только ID, имя, фамилию, org-role и дату вступления. `emit_empty_slices` включён в изолированной sqlc конфигурации. В ответах не обнаружены email/phone/password/session.
- FK и уникальность org/user заданы миграцией025. Изменения существующих таблиц/legacy permission predicates в A1 не внесены. Тестовая очистка добавляет organizations к уже существующему isolated test truncate.
- UI соблюдает границу A1, явно предупреждает об отдельности личного учебного кабинета, использует выбранный ID только для настроек. Query keys включают user ID/sessionVersion/org ID; смена аккаунта размонтирует Workspaces. Member-list не запрашивается обычной ролью. Ввод сохраняется при обычном PATCH failure; POST не повторяется автоматически, неоднозначная ошибка требует обновить список.
- Новая организация не заявляется готовой школой с общими учебными данными. Полная межорганизационная изоляция, приглашения, родители, курсы, ДЗ, дневник и реальные тарифы по-прежнему зависят от A2–D.

Неблокирующее UX-замечание: после успешного сохранения сообщение «Настройки сохранены» не очищается при следующем изменении draft. Активная кнопка и navigation guard учитывают dirty state, но успех может восприниматься как подтверждение новых правок. Рекомендуется очищать старый success при изменении поля.

Остаются обязательными подтверждения координатора/tester: реальные результаты API на разных ролях/организациях, rollback и регрессии, lint/build, браузерные сценарии desktop/360px и смена аккаунта. Архитектурное чтение не подтверждает ни runtime tenant isolation legacy данных, ни готовность полного BRD MVP, ни production миграцию.
