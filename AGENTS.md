# ent-ready: инструкции для команды разработки

## Проект

- Frontend: `frontend/`, Next.js 16 App Router (версия в package-lock.json), React 19, TypeScript, Tailwind 4, React Query, Zustand, Axios.
- Backend: Go 1.25, Gin; маршруты в `handler/routes.go`, API `/api/v1`.
- Данные: PostgreSQL, pgx/v5, sqlc; источники в `db/queries/` и `db/migrations/`, генерация в `db/sqlc/`.
- Основные сценарии: учителя, студенты, группы, уроки, тесты, банк вопросов и ЕНТ.
- В `frontend/` также действуют инструкции `frontend/AGENTS.md`. Прочти их до изменений фронтенда.

## Работа команды

Основной агент — координатор и интегратор. Пользователь описывает задачу в основном чате; координатор доводит её до результата.

Команда включает также `tester` и `business_analyst`. Бизнес-аналитик исследует потребности, аналоги и идеи в `docs/product/`; системный аналитик/архитектор переводит выбранные идеи в требования и технический план. Исследование не означает автоматическое включение идеи в разработку.

`ux_ui_designer` проектирует пользовательские сценарии, структуру и состояния экранов, адаптивность и доступность. Спецификации сохраняет в `docs/design/`, опираясь на существующие компоненты и визуальный язык. Для задач интерфейса подключай его после уточнения требований и до реализации frontend; после реализации назначай дизайн-ревью. Для небольших правок не требуй отдельного полного дизайн-этапа.

Поток работы для редизайна: `business_analyst` (актуальные аналоги, проблема, продуктовая постановка) → `ux_ui_designer` (сценарии, дизайн-система и прототип) → `architect` (финальное ТЗ фронтенду с привязкой к API и файлам) → `frontend`/`backend` (реализация в согласованном объёме) → `tester` и `ux_ui_designer` (проверка поведения и дизайна). Архитектор может заранее консультировать по ограничениям, но финальное ТЗ составляет после дизайн-концепции. Изменения API выноси отдельными зависимостями до реализации. Дизайнер не редактирует одновременно с разработчиком одни и те же файлы. Текущий выбранный пользователем стиль — спокойный учебный интерфейс.

После реализации назначай независимую проверку `tester`: негативные и разрешённые сценарии, регрессии, реальные результаты команд. Тестировщик работает на изолированной тестовой БД. При ограничении числа одновременных агентов выполняй этапы последовательно: анализ → разработка → тестирование; исследование продукта планируй отдельно.

Используй субагентов `architect`, `frontend` и `backend` из `.codex/agents/` для задач соответствующих ролей. Для небольшой локальной правки привлекай только необходимую роль.

1. Изучи состояние рабочей копии, применимые инструкции и существующую реализацию. Сохраняй изменения пользователя.
2. Для задач нескольких слоёв сначала поручай `architect` требования, критерии приёмки, API-контракт и распределение файлов. Не выдумывай бизнес-правила; фиксируй предположения.
3. После согласования контракта запускай независимые задачи frontend и backend параллельно. Укажи каждому агенту его файлы, ожидаемый результат и проверки.
4. Не поручай нескольким агентам одновременное редактирование одного файла. Общие конфиги, зависимости, API-клиент и маршруты закрепляй за конкретным исполнителем.
5. Агенты возвращают список изменений, проведённые проверки и проблемы интеграции. Координатор разрешает противоречия и проверяет весь пользовательский сценарий.
6. Для существенных изменений поручай архитектору финальную проверку требований и контракта. Исправляй найденные ошибки до завершения.

## Проверки и ограничения

- Frontend: из `frontend/` запускай `npm run lint` и `npm run build` при изменениях интерфейса. Сначала прочти документацию установленного Next.js согласно вложенному AGENTS.md.
- Backend: форматируй изменённый Go-код; запускай `go test ./...` и `go vet ./...`. Учитывай требования `testutil/` и используй только тестовую БД.
- SQL: изменяй источники, затем запускай `sqlc generate`; не редактируй генерируемые файлы вручную.
- Проверяй серверную авторизацию, владение ресурсами и отсутствие утечек ответов тестов; скрытие кнопки в UI не заменяет проверку прав на сервере.
- Не записывай реальные секреты в файлы и отчёты. Изменения конфигурации описывай в `.env.example` без секретов.
- Не переписывай применённые миграции. Production-миграции, публикация и разрушительные операции требуют разрешения пользователя.
- Не добавляй зависимости и не меняй архитектуру без необходимости для задачи.
- В финале сообщай результат, реально выполненные проверки и оставшиеся ограничения. Не выдавай незапущенные проверки за успешные.
